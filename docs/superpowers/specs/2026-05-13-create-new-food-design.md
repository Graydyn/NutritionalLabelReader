# Create New Food — Design

Date: 2026-05-13
Module: `:tracker`
Screen: Add Food (`SearchScreen`)

## Goal

Let the user add a food to the local Room database from inside the Add Food screen, without leaving the screen. After saving, the new food is auto-selected so the user can immediately enter grams and log it as a diary entry — the same end-state as picking a search hit.

## Motivation

The bundled CSV (`assets/nutrition_foundation.csv`, ~363 items) is finite. The only way to record anything outside it today is the OCR scan flow on `DiaryScreen`, which produces an ad-hoc `DiaryEntry` and adds nothing to the food database. There is no path to grow the database from inside the app.

## UI

### Button

- Component: Material 3 `OutlinedButton`, full width.
- Label: "Create new food".
- Location: in `SearchScreen.kt`'s outer `Column`, directly below the search `OutlinedTextField`, before the `if (results.isEmpty())` branch.
- Visibility: always shown, regardless of query or results state.
- Action: sets `SearchViewModel.showCreateDialog = true`.

### Modal

Standard Material 3 `AlertDialog`, opened when `showCreateDialog` is true.

- Title: "New food".
- Body: `Column` of five `OutlinedTextField`s, in order:
  1. **Name** — required, default keyboard. Pre-filled from `SearchViewModel.query.value.trim()` if non-blank when the dialog opens; otherwise empty and gets initial focus.
  2. **Calories per 100 g** — required, decimal keyboard.
  3. **Protein per 100 g** — optional, decimal keyboard.
  4. **Fat per 100 g** — optional, decimal keyboard.
  5. **Carbs per 100 g** — optional, decimal keyboard.
- Buttons: "Cancel" (dismiss, discard all input), "Save" (commit and close).
- Save is enabled only when:
  - Name (after trim) is non-blank, AND
  - Calories parses as a non-negative `Float`.
- Inline captions under any field that fails its own validation:
  - Name blank → "Required".
  - Calories blank → "Required".
  - Calories non-numeric → "Must be a number".
  - Calories negative → "Must be 0 or greater".
  - Optional macros never show a caption (non-numeric input is silently coerced to null).
- Dialog field state lives in `remember { mutableStateOf("") }` inside the dialog composable. It is recreated on each open and discarded on dismiss.

## Data layer

No schema change. The existing `Food` entity already has nullable macros and an autogenerated PK with no unique constraint on `name`.

### `FoodDao` — add a single-insert returning the new row id

```kotlin
@Insert(onConflict = OnConflictStrategy.IGNORE)
suspend fun insert(food: Food): Long
```

`OnConflictStrategy.IGNORE` matches the existing `insertAll`. With no unique constraint on `name`, every insert produces a new row; this is the mechanism by which "allow duplicates silently" works.

### `FoodRepository` — wrap it

```kotlin
suspend fun add(food: Food): Long = dao.insert(food)
```

## ViewModel

All changes go in `SearchViewModel.kt`.

### New state

```kotlin
private val _showCreateDialog = MutableStateFlow(false)
val showCreateDialog: StateFlow<Boolean> = _showCreateDialog.asStateFlow()
```

Per-field input is **not** held in the ViewModel — it lives in the dialog composable so it is naturally scoped to the dialog's lifetime.

### New actions

```kotlin
fun openCreateDialog() { _showCreateDialog.value = true }
fun dismissCreateDialog() { _showCreateDialog.value = false }

fun createFood(
    name: String,
    calories: Float,
    protein: Float?,
    fat: Float?,
    carbs: Float?
) {
    viewModelScope.launch(Dispatchers.IO) {
        val food = Food(
            name = name.trim(),
            caloriesPer100g = calories,
            proteinPer100g = protein,
            fatPer100g = fat,
            carbsPer100g = carbs
        )
        val id = foodRepo.add(food)
        val saved = food.copy(id = id)
        withContext(Dispatchers.Main) {
            _selectedFood.value = saved
            _grams.value = ""
            _query.value = saved.name
            _showCreateDialog.value = false
        }
    }
}
```

The dialog composable parses input strings into `Float?` (using `String.toFloatOrNull()` and treating non-numeric optional fields as null, matching `CsvSeeder.parseNullableFloat`) and only invokes `createFood` once its own validation has passed.

## Save → auto-select flow

After `createFood` completes the screen lands in the same state as a normal search-and-select:

1. `_query.value = saved.name` triggers the existing debounced `searchResults` flow, which re-queries the DB and includes the new row.
2. `_selectedFood.value = saved` makes the existing `FoodResultCard` render in its selected state, with the grams `OutlinedTextField` and "Add" button visible (existing `AnimatedVisibility` block at `SearchScreen.kt:264`).
3. The user types grams and taps "Add" — uses the existing `logEntry` code path. No new logging logic.

Known timing wrinkle: `_query` is debounced 300 ms before `searchResults` repopulates, so the screen briefly shows `EmptyState` after the dialog closes. This is acceptable and matches existing search behavior. Not optimizing pre-emptively.

## Daily totals contract

Foods saved with null macros (e.g., calories only) contribute null on those macros to any future `DiaryEntry` they back. `DiaryViewModel.dailyTotals` already sums macros with `?: 0` / `?: 0f`, so missing values are treated as zero. This matches existing behavior for both the seeded CSV (which has gaps) and OCR-scanned entries. No change to totals logic.

## Edge cases handled

- Empty/whitespace-only name → Save disabled.
- Calories non-numeric or negative → Save disabled with caption.
- Optional macros left blank → saved as null. Blank is not zero.
- Optional macros that are non-numeric → treated as blank (null), not a save block.
- Cancel / back dismiss → no DB write, all field state discarded.
- Duplicate names → silently allowed.
- Pre-fill: query non-blank → Name pre-filled with `query.trim()`, cursor at end; query blank → Name empty, gets initial focus.
- Process death while dialog open → dialog closes, no partial DB write. User re-taps the button.

## Non-goals

- Editing existing foods.
- Deleting foods.
- Per-serving (vs per-100 g) input.
- Image / brand / barcode fields.
- Undo after save.
- Duplicate detection / merging.
- Automated tests for this feature. The `:tracker` module has no existing test harness; we continue to rely on manual verification.
